# Contributing

How a change gets into Marid: licences and headers, the clean-room rule, DCO sign-off, the merge form, the local checks, the git hooks, and who reviews what. Written from `CONTRIBUTING.adoc`, `.github/CONTRIBUTING.md`, `docs/contributing.adoc`, `docs/audits/licensing.adoc`, `docs/MARID-FRAMEWORK.adoc` ("Licensing"), `.github/CODEOWNERS`, `.githooks/`, `.github/workflows/dco.yml` and the `Justfile`. For who decides, see [[Governance]]; for the CI gates a PR must pass, see [[CI-and-Operations]]; for setting up a working tree, see [[Onboarding]].

## Before you start

- Read `PROJECT_BRIEF.md` (the product and engineering contract) and `AGENTS.md` (repository instructions for coding agents). `CONTRIBUTING.adoc` at the root points to `.github/CONTRIBUTING.md` for the full workflow and to `.github/CODE_OF_CONDUCT.md`, and asks you to follow the language policy in `CLAUDE.md`.
- Significant changes (new features, breaking changes, architectural shifts) are discussed in an issue before implementation (`.github/GOVERNANCE.md`).
- Non-obvious design decisions are written up as ADRs in `docs/decisions/` (see [[Decisions]]). Statuses are `proposed`, `accepted`, `deprecated`, `superseded`, `rejected`.
- Report security vulnerabilities privately through GitHub Security Advisories at `github.com/metadatastician/marid/security/advisories/new`, never through a public issue (`CONTRIBUTING.adoc`, `.github/SECURITY.md`).

## Licences and the exact headers

The licensing model is dual (`docs/audits/licensing.adoc`, audited 2026-09-19; `docs/MARID-FRAMEWORK.adoc`, "Licensing"):

| Artifact | Licence | Applies to |
|---|---|---|
| Source code and authored tooling | **MPL-2.0** (file-level copyleft, standard text, no "MPL variant") | Julia packages under `packages/`, AffineScript/JS under `web/`, Zig and Idris2 ABI files under `src/interface/`, Just recipes, shell scripts, test suites |
| Documentation and artwork | **CC-BY-SA-4.0** | Everything under `docs/`, README files, diagrams, guides; `docs/` carries its own LICENSE |
| Code snippets inside documentation | **MPL-2.0**, stated explicitly in the doc header | Samples embedded in `.adoc` files may be reused under MPL-2.0 without copyleft on the enclosing prose |
| Third-party dependencies | Various (permissive) | Pinned in `THIRD_PARTY_NOTICES.md` with upstream notices preserved |

Every source file, document, script and manifest carries an SPDX header; CI enforces it. The exact header texts from `docs/MARID-FRAMEWORK.adoc`:

Julia (and other `#`-commented code):

```julia
# SPDX-License-Identifier: MPL-2.0
#
# This Source Code Form is subject to the terms of the Mozilla Public
# License, v. 2.0. If a copy of the MPL was not distributed with this
# file, You can obtain one at https://mozilla.org/MPL/2.0/.
```

Documentation:

```html
<!-- SPDX-License-Identifier: CC-BY-SA-4.0 -->
```

AsciiDoc files in this repository carry the same identifier as a `//` comment on line one (`// SPDX-License-Identifier: CC-BY-SA-4.0`), as every `.adoc` source read for this page does.

Generated-code policy (`docs/audits/licensing.adoc`):

- The IR definition in `packages/MaridIR/` is original MPL-2.0 code.
- Schema files generated by Marid tools into `contracts/` (OpenAPI 3.1 JSON, GraphQL SDL, `.proto`, `.capnp`, `.bop`) from a user's `MaridIR` services carry the user's licence; the generator templates are MPL-2.0.
- Browser client code emitted by `MaridOpenAPI` or `MaridGraphQL` is treated as user code; Marid claims no copyright over it.

## Clean-room discipline

Marid is inspired by Genie.jl (MIT). The boundary is strict (`docs/audits/licensing.adoc`; `docs/MARID-FRAMEWORK.adoc`):

1. No code or test fixtures are copied or adapted from Genie.jl. Study behaviour, copy nothing.
2. No Genie-specific internal APIs or macro conventions are cloned.
3. Marid differentiates itself structurally: an immutable intermediate representation (`MaridIR`), pure trie routing separated from transport, streaming symmetric handlers, first-class native protocol adapters.
4. No "Genie" in names, logos or package descriptions beyond factual attribution ("inspired by"). The notice of inspiration is recorded in `THIRD_PARTY_NOTICES.md` and the framework charter ([[Charter]]).

## DCO sign-off on every commit

Contributions are accepted under the Developer Certificate of Origin, not a CLA (`PROJECT_BRIEF.md`; `docs/audits/licensing.adoc`; `docs/MARID-FRAMEWORK.adoc`). Every commit needs a `Signed-off-by` trailer:

```bash
git commit -s -m "feat(core): describe the change"
```

`.github/workflows/dco.yml` ("DCO Sign-off Enforcement") runs on every pull request (`opened`, `synchronize`, `reopened`), walks `base..head`, and fails if any commit message lacks a line matching `^Signed-off-by: .+ <.+@.+>$`.

Sign-off is distinct from signing. `docs/contributing.adoc` and `.github/SECURITY.md` ask for signed commits (`git config commit.gpgsign true`), and the `required_signatures` rule in force on `main` (see [[Governance]]) rejects unsigned commits at push. Do both: sign the commit and add the sign-off trailer.

## Merge form

Squash is the merge form. Rebase-merge is disabled: replaying commits in a rebase merge produces unsigned commits on `main`, which `required_signatures` then rejects. `docs/contributing.adoc` asks that auto-merge be armed on every PR you open:

```bash
gh pr merge <num> --auto --squash
```

A PR merges when the required checks pass and reviews land.

## Branches and commit messages

Two sources give branch conventions:

| Source | Convention |
|---|---|
| `.github/CONTRIBUTING.md` | `docs/<short-description>`, `test/<what-added>`, `feat/<short-description>`, `fix/<issue-number>-<description>`, `refactor/<what-changed>`, `security/<what-fixed>` |
| `docs/contributing.adoc` | `claude/<topic>` for AI agents, `<initials>/<topic>` for humans |

Both ask for Conventional Commits (`<type>(<scope>): <description>`; types `feat`, `fix`, `chore`, `refactor`, `docs`, `test`, `ci`, `revert`). The CHANGELOG is generated from them. Keep commits focused: one logical change per commit. Look for issues labelled `good first issue`, `help wanted`, `documentation` and `perimeter-3` for a first contribution.

## Adding a dependency

From `docs/contributing.adoc`: state in the PR body what the dependency unlocks; check provenance (maintained, audited, no malicious history); pin to a SHA, not a tag; record it in the architecture document's dependency section. New direct dependencies are also checked against the permitted-licence allowlist in `docs/audits/licensing.adoc` (HTTP.jl, JSON3.jl, StructTypes.jl, GraphQLite.jl, Capnp.jl, libnghttp2 are MIT; ArangoDB Community Server is Apache-2.0 and accessed only over HTTP; `@hyperpolymath/affinescript`, `EchoTypes.jl` and `Cladistics.jl` are MPL-2.0 estate imports).

Package tests run in each package's own environment (`julia --project=packages/<Pkg> -e 'using Pkg; Pkg.test()'` after `scripts/bootstrap.jl`; see [[Onboarding]]). Mocks never prove interoperability: every integration needs a real interop or database integration test.

## Git hooks

`.githooks/` holds the local Dogfood Gate. Enable it once per clone:

```bash
.githooks/install.sh      # sets core.hooksPath -> .githooks; or: just install-hooks
```

| File | Role |
|---|---|
| `.githooks/pre-push` | Runs the same DEED and K9 validators the CI Dogfood Gate runs, on the refs being pushed, before the push leaves |
| `.githooks/validate-deed.sh` | DEED manifest validator (skipped gracefully if its tooling is absent) |
| `.githooks/validate-k9.sh` | K9 contract validator (same skip rule) |
| `.githooks/scan-secrets.sh` | Secret scan; **fails closed**: a missing scanner blocks the push, because "validator absent" and "no secrets found" would otherwise be indistinguishable |
| `.githooks/install.sh` | Idempotent installer |

Emergency override: `git push --no-verify`. The vendored validators are byte-identical to the pinned CI action scripts and are refreshed by the estate `refresh-githooks` sweep.
